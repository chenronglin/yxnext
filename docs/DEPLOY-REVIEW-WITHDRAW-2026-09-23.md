# 作者撤回与编辑开始审核：实施上线说明

## 1. 本次发布范围

基线为上次提交 `ec691f4`（可以反复修改项目计划），目标为本次修改完成后形成的发布提交。当前改动尚未提交，实施前必须先提交完整代码并记录实际发布提交号，不能把基线提交号当作新版发布号。

本次是一次完整升级，包含作者撤回、编辑显式开始审核、并发保护及配套历史/通知/待办显示。中间开发版本没有上线，不作为迁移前提。

| 内容 | 上次提交 | 本次上线后 |
| --- | --- | --- |
| 作者提交后修改 | 等待编辑退回 | 编辑开始审核前，可撤回修改再提交 |
| 撤回限制 | 无此功能 | 不设时间或次数限制 |
| 编辑打开稿件 | 按原权限直接操作 | 先只读预览，点击“开始审核”后才能修改、批注、通过或退回 |
| 开始审核后 | 无显式开始标记 | 本轮立即禁止撤回，即使编辑尚未保存修改 |
| 再次提交 | 原有交接流程 | 新一轮重新等待开始审核 |
| 历史与待办 | 提交/通过/退回 | 增加撤回历史及通知；撤回关闭本轮审核待办，重提新建待办 |
| 旧窗口 | 原有锁版本校验 | 增加草稿批次校验，防止旧页面影响重提后的稿件 |

适用于梗概、细纲、正文章节和质检稿。既有项目权限、阶段条件及管理员代审核权限保留；报表继续统计实际提交次数，撤回重提会产生新的提交记录。

## 2. 数据库变更和存量数据

相对基线，本次只新增这一份迁移：

```text
20260923000000_add_explicit_review_start
```

迁移同时完成三个结构变更和一次数据回填：

- `doc_current_drafts.review_started_at`：新增可空审核开始时间。
- `docs.last_action`：增加 `author_withdraw`、`editor_start_review` 枚举值。
- `doc_revisions.action`：增加 `author_withdraw` 枚举值。
- 对 `owner_role = 'editor' AND save_count > 0` 的已有草稿，以 `updated_at` 回填开始时间；没有保存过的编辑稿保持未开始，作者稿不回填。

已有正文、批注、版本、待办和通知不会被迁移删除。回填时间是旧稿兼容标记，不是历史用户点击按钮的真实时间。

基线包含六份历史迁移，最近一份为 `20260902000000_add_basic_upgrade_features`。若线上确实运行基线版本且历史迁移齐全，部署时应仅有上述一份新迁移待执行；若出现其他待执行迁移或历史不一致，先核对实际线上版本，不能直接套用本说明。

不需要新增环境变量、统一时间配置或管理员初始化操作；依赖、Nginx 和服务端口均未修改。

## 4. 正式上线顺序

### 4.1 停止旧版写入并备份

提前告知用户维护窗口，请用户完成保存。开启现有维护入口，随后在**旧生产目录**执行：

```bash
./run.sh status
./run.sh stop
lsof -nP -iTCP:13100 -sTCP:LISTEN
```

确认监听进程已退出，多实例全部停止，没有后台任务继续写同一数据库。保存旧应用目录、构建包、环境配置及日志，然后通过现有数据库备份流程完成可恢复备份，记录快照/备份标识。最终备份应在写入停止后完成，覆盖迁移前的完整状态。

### 4.2 检查并执行一次迁移

切换到**新发布目录**，确认使用正确的生产 `DATABASE_URL`，再执行：

```bash
npx prisma migrate status
npx prisma migrate deploy
npx prisma migrate status
```

第一次状态检查应仅显示本次新迁移待执行（有待执行迁移时可能返回非零退出码）；迁移后的状态检查应显示数据库已同步。使用 `migrate deploy`，不使用 `migrate dev`、`db push` 或手工标记已执行替代迁移。

迁移成功后，在数据库管理工具中检查：

```sql
SELECT migration_name, finished_at, rolled_back_at
FROM _prisma_migrations
WHERE migration_name = '20260923000000_add_explicit_review_start';

SHOW COLUMNS FROM doc_current_drafts LIKE 'review_started_at';
SHOW COLUMNS FROM docs LIKE 'last_action';
SHOW COLUMNS FROM doc_revisions LIKE 'action';

-- 正常为 0：旧编辑保存稿已全部标记为审核开始。
SELECT COUNT(*) AS missing_review_start
FROM doc_current_drafts
WHERE owner_role = 'editor' AND save_count > 0 AND review_started_at IS NULL;
```

迁移记录应 `finished_at` 非空、`rolled_back_at` 为空，字段和枚举包含第 2 节列出的全部变更。

### 4.3 启动新版本

确认新目录已完成 Prisma Client 生成和生产构建，然后启动：

```bash
./run.sh start
./run.sh status
tail -n 100 app.log
curl --fail --silent --show-error --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:13100/login
```

确认登录页返回 `200`，日志无缺字段、未知枚举或 Prisma 错误；通过实际公网入口再次检查登录与稿件访问。完成下节验收后解除维护入口。

不能让旧版和新版同时对外提供稿件写入服务；旧版不知道“开始审核”标记，会破坏新版撤回条件。通知用户刷新已经打开的稿件页：本次写接口新增必填草稿 ID，旧页面不能继续用于保存和审核。

## 5. 业务验收

使用专用测试项目完成以下检查，避免修改真实业务稿件：

1. 作者保存并提交；编辑打开稿件，只能预览，显示“开始审核”。作者此时可撤回，正文和批注保留，恢复可编辑状态。
2. 撤回后检查提交及撤回历史、编辑通知、本轮审核待办关闭；修改重提后产生新的审核待办。重复撤回重提确认没有次数限制，页面没有倒计时或期限配置。
3. 编辑点击“开始审核”，确认可修改、批注、通过及退回；尚未保存任何内容时，作者也已经不能撤回。
4. 作者页和另一编辑页保持打开，确认状态自动同步；旧编辑页面遇到作者撤回后停止操作，不能覆盖新一轮稿件。
5. 编辑退回，作者修改重提，确认重新等待“开始审核”；再完成开始审核、保存和通过。
6. 分别抽查升级前已保存和未保存的待审编辑稿：前者保留审核权限且不可撤回，后者需点击开始审核且仍允许作者撤回。
7. 抽查管理员代审核及非项目成员权限，确认原有权限边界有效；检查日志没有持续错误。

梗概、细纲、正文和质检稿共用服务逻辑；测试环境应覆盖四类稿件。无时间限制和并发争抢已由自动化测试验证，无需在线等待或修改生产提交时间。

## 6. 异常与回退

- **构建失败且尚未进入维护窗口**：保持旧服务运行，修复后重新准备发布包。
- **迁移失败**：保持服务停止，保存错误信息并核对实际字段和 `_prisma_migrations`。MySQL 的结构变更可能部分生效，不能假定自动全部回滚，也不能盲目重跑 SQL 或删除迁移记录。
- **迁移成功但新版无法启动，尚未开放业务**：可恢复维护窗口内的数据库备份及旧应用，二者一起回到已知基线；恢复前核对期间是否有任何新写入。
- **新版已产生撤回/开始审核记录**：优先停止写入并向前修复。旧版 Prisma 枚举不认识新增动作，不能只切回旧应用并假设兼容；直接恢复旧备份又会丢失上线后的业务数据，应先保全数据并制定针对性的恢复方案。

本次不提供删除字段或收缩枚举的自动回滚脚本，不覆盖已经产生的新业务历史。

## 8. 本地开发环境同步

本地测试库也必须执行本次迁移。仅更新代码或执行 `prisma generate` 不会新增数据库字段；若日志出现 `doc_current_drafts.review_started_at` 不存在，稿件读取会返回服务器错误，不能据此判断作者权限或稿件丢失。

确认 `.env` 指向本地测试库并备份后，执行 `npx prisma migrate deploy`，再执行 `npx prisma generate`，启动或重启开发服务并刷新稿件页。`npx prisma migrate status` 应显示数据库已同步。

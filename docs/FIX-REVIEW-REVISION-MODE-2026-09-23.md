# 开始审核后修订未生效：修复记录

## 原因和影响

基线版本：`fac228b`（作者可以撤回提交的文档）。编辑打开待审稿件时，编辑器以只读、关闭修订的配置初始化。点击“开始审核”后，React 更新了 `editable` 和 `trackChanges`，但 Tiptap 的 `setOptions({ extensions })` 不会重建已注册插件；结果是正文可以修改，实际修订插件仍然关闭。

切换章节再回来会重新创建编辑器，所以能恢复修订，与用户反馈一致。故障期间可能直接修改正文，属于真实未生成修订数据，不只是颜色或侧栏显示问题。

## 修复

- 修订开关和编辑人信息保存在各 Editor 实例自己的运行时状态中，通过专用命令同步。
- 从预览进入审核时，先同步修订配置，再开放正文输入。
- 输入、删除、替换、粘贴、拖放、剪切、中文输入及工具栏统一读取运行时配置。
- 保持编辑器实例不变，保留当前正文、选区和撤销历史；模式切换不产生正文保存。
- 切换修订模式时若仍有中文输入等待补标，暂缓新的输入，等待该次输入完成修订后再切换。

## 验证

新增真实 React + Tiptap 组件测试，复现修复前的 5 个失败场景；修复后 8 项测试通过，覆盖原地开始审核后的新增、删除、替换、粘贴、中文输入、批注、保存数据、撤销历史及作者普通编辑。

原有 270 项常规测试通过；隔离 MySQL 的 11 项事务集成测试通过。类型检查、修改文件的 ESLint、生产构建和 diff 检查通过。

浏览器使用独立测试库实测：点击开始审核后直接输入出现新增修订，删除原文出现删除修订，再添加批注。数据库确认保存了 2 条修订、1 条批注；刷新页面后仍完整显示。未改写用户现有稿件。

## 发布及已有稿件

本次仅为编辑器修复，无新增迁移、依赖或环境变量。基线版本已完成迁移的环境，只需构建、发布并通知编辑刷新已打开的稿件页。未升级过的环境仍按原功能上线说明执行迁移。

故障期间已经保存且没有修订标记的改动，不会自动补回标记。应保留当前稿件，并与本轮作者提交的历史快照比较后再决定恢复方式；不能直接以旧稿覆盖当前编辑成果。
